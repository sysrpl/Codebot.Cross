# macOS Web View Controls: Instructions

This folder is where we build the macOS version of the Codebot web view controls. The goal is for TWebBrowser, TWebInspector, TWebAddressBar, and TWebStatusIndicator to work on macOS with the Cocoa widgetset as much like they work on Linux and Windows as possible, so a form built on one platform runs the same on the others.

The work is done on a Mac, where it can be compiled and tested.

## What already exists

The controls live in `source/codebot_webkit`. Read these files first:

| File | What it does |
| --- | --- |
| `codebot.webkit.controls.pas` | The shared unit. Declares TWebBrowser, TWebInspector, and TWebDownload, and does all the platform independent work. It picks a backend unit in its uses clause with `{$ifdef lclgtk3}`. |
| `codebot.webkit.controls.extras.pas` | TWebAddressBar and TWebStatusIndicator. These only talk to TWebBrowser, so they should work on macOS unchanged. |
| `codebot.webkit.controls.gtk3.pas` | The Linux backend, built on WebKitGTK. |
| `codebot.webkit.controls.win.pas` | The Windows backend, built on WebView2. This is the best model for macOS, as it also maps a foreign API onto the WebKitGTK style values. |
| `codebot.interop.webkit.pas`, `codebot.interop.webview2.pas` | The API declarations for each engine. |
| `webkit.inc` | Stops the build on any widgetset other than gtk3 or win32. |
| `README.md` | What the controls do from the user's point of view. The macOS version has to match this. |

## How a backend plugs in

Each backend unit is wrapped in an `{$ifdef}` for its platform and declares the same things:

- The `WEBKIT_LOAD_*`, `WEBKIT_HIT_TEST_RESULT_CONTEXT_*`, and `WEBKIT_SCRIPT_DIALOG_*` constants, with the same values as WebKitGTK.
- `IWebBrowserEvents` and `IWebInspectorEvents`, with the same GUIDs and methods. TCustomWebBrowser and TWebInspector implement them, and the backend calls them when something happens in the web view.
- `TWSWebBrowser`, a widgetset class with the same class methods: CreateHandle, Load, LoadHtml, Stop, Reload, GetLoading, ExecuteScript, BackOrForward, BackOrForwardExists, SetEditable, SetZoomFactor, SetZoomTextOnly, SetDeveloperTools, ShowInspector, Print, CaptureToClipboard, HistoryItem, Download, CancelDownload, and DownloadFolder.
- `TWSWebInspector`, with CreateHandle, Open, and Close.
- `InitWebKit`, which returns True when the engine can be used. TCustomWebBrowser.Available calls it.

The macOS backend has to provide exactly the same declarations, so the shared unit does not need to know which platform it is on.

## The macOS engine

macOS ships WebKit.framework as part of the system, so there is nothing to install or bundle. Use `WKWebView`, not the old `WebView` class, which Apple deprecated in macOS 10.14.

The work is in Free Pascal with `{$modeswitch objectivec2}` and the CocoaAll units. The WebKit headers that come with FPC may only cover the old WebView class, so we will probably need to declare the WK classes and protocols we use ourselves, in a unit like `codebot.interop.wkwebview.pas`. Check what FPC provides before writing them.

The LCL Cocoa widgetset gives each TWinControl an NSView. The WKWebView is added as a subview of the control's view with an autoresizing mask, so it should not need the Resize handling that Windows needs.

## Mapping the features

| Feature | How to do it on macOS |
| --- | --- |
| Load, LoadHtml | `loadRequest:`, and `loadHTMLString:baseURL:` with `about:blank` as the base so the shared unit's about:blank check still works |
| Stop, Reload, GetLoading | `stopLoading`, `reload`, `isLoading` |
| Location and title changes | Key value observing on `URL` and `title` |
| Progress | Key value observing on `estimatedProgress`, scaled to 0..100 |
| Load status | WKNavigationDelegate: `didStartProvisionalNavigation` is started, `didReceiveServerRedirect` is redirected, `didCommitNavigation` is committed, `didFinishNavigation` is finished |
| OnError | `didFailProvisionalNavigation` and `didFailNavigation` |
| OnNavigate | `decidePolicyForNavigationAction:decisionHandler:` |
| History | `goBack`, `goForward`, `goToBackForwardListItem:`, and `backForwardList` for BackOrForwardExists and HistoryItem. Unlike Windows, this should support more than one step. |
| ExecuteScript | `evaluateJavaScript:completionHandler:` |
| Script dialogs | WKUIDelegate `runJavaScriptAlertPanel`, `runJavaScriptConfirmPanel`, and `runJavaScriptTextInputPanel`. Call the completion handler with the result from ViewScriptDialog. |
| ZoomFactor | `pageZoom` (macOS 11 and later), or `magnification` |
| ZoomTextOnly | Probably not supported. Note it as a difference, like Windows. |
| Editable | Set `document.designMode` with a script after each load, as there is no direct property |
| Hover link and hit testing | No direct API. Use a user script that reports the element under the mouse through a WKScriptMessageHandler. |
| Context menu | Override `willOpenMenu:withEvent:` on a WKWebView subclass, or use the same script approach |
| Downloads | WKDownload and WKDownloadDelegate (macOS 11.3 and later). `navigationResponse:didBecomeDownload:` starts one, `decideDestinationUsingResponse` asks for the file name, and progress comes from the download's NSProgress. |
| DownloadFolder | `NSSearchPathForDirectoriesInDomains` with NSDownloadsDirectory |
| CaptureToClipboard | `takeSnapshotWithConfiguration:completionHandler:`, then put the image on the general pasteboard |
| Print | `printOperationWithPrintInfo:` and run it modally |
| DeveloperTools | `isInspectable` (macOS 13.3 and later), or the `developerExtrasEnabled` preference on older systems |
| TWebInspector | There is no public API for showing the inspector inside another view. Find out what is possible, and if nothing is, TWebInspector should behave like Windows without its debugging server: the inspector opens in a window of its own, and the docs say so. |

## Questions to settle on the Mac

1. **Where the code ends up.** The shared unit chooses its backend with an `{$ifdef}`, so it has to name the macOS unit. Either the units built in this folder move into `codebot_webkit` with a small change to its uses clause, `webkit.inc`, and the lpk, or this folder becomes its own package that codebot_webkit requires on darwin. Decide this before writing much code.
2. **Which version of macOS to require.** Downloads need 11.3 and isInspectable needs 13.3. Choose the lowest version worth supporting, and use the newer features only when they are available.
3. **How much of the hit testing and context menu can be matched.** These are the features least like the other platforms.

## Steps

1. Build and run the existing package on the Mac to confirm that the Cocoa widgetset and the compiler work.
2. Settle the questions above.
3. Write the WKWebView declarations we need.
4. Write the backend with TWSWebBrowser.CreateHandle and Load first, and get a page showing in a TWebBrowser.
5. Add the features in the order of the table above, testing each one against the same test program on Linux or Windows.
6. Make TWebAddressBar and TWebStatusIndicator work against it, which should need no changes.
7. Work out TWebInspector.
8. Update `README.md` and the unit docs with a macOS section listing the differences, in the same style as the Windows section.

## Rules

- Match the style of the existing code: `{$i webkit.inc}`, delphi mode, the header block, short comments in braces above each routine, and the same names as the other backends.
- Don't change how the controls behave on Linux or Windows.
- When something can't work the same way on macOS, keep it as close as possible and write the difference down in the docs, as the Windows section of the README does.
